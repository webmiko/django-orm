# Безопасность данных и защита от взлома

Документ составлен по ревью кода и `config/settings.py` на момент создания вики. Проект учебный: часть мер применима только к **продакшену**.

---

## Что уже сделано хорошо

1. **CSRF** — включён `CsrfViewMiddleware`; формы используют `{% csrf_token %}` (выход — POST).  
2. **Пароли** — стандартные `AUTH_PASSWORD_VALIDATORS` Django; хеширование через фреймворк авторизации.  
3. **Секретный ключ** — при `DEBUG=False` без `SECRET_KEY` в окружении приложение не стартует; запрещено использовать dev-ключ в продакшене (см. `settings.py`).  
4. **SQL-инъекции** — запросы через ORM и параметризованные формы; сырых SQL в проекте не найдено.  
5. **XSS в шаблонах** — не используются `|safe` / `mark_safe` для пользовательского контента в найденных шаблонах; автоэкранирование Django по умолчанию.  
6. **Загрузка файлов** — проверка размера, MIME (если передан), сигнатуры JPEG/PNG (`config/image_validation.py`).  
7. **Секреты в репозитории** — `.env` в `.gitignore`; есть `.env.example` без реальных паролей.  
8. **Базы и логи** — `*.sqlite3`, `*.log`, каталог `logs/` игнорируются git.  
9. **Clickjacking** — `XFrameOptionsMiddleware` включён.  
10. **Профиль** — `UserProfileView.get_object()` возвращает только `request.user`; чужой аккаунт через эту форму не отредактировать.

## Риски и ограничения (важно)

### 1. Нет разграничения прав на объекты (IDOR)

Любой **вошедший** пользователь может:

- создавать/редактировать/удалять **любой** товар;  
- создавать/редактировать/удалять **любой** пост блога  

Проверяется только факт входа (`LoginRequiredMixin`), а не роль или владелец записи. Для продакшена нужны группы/права (`PermissionRequiredMixin`), флаг персонала или проверка автора записи.

### 2. Регистрация открыта для всех

Любой может создать учётную запись; нет подтверждения email, капчи и лимитов. Для публичного сервиса обычно добавляют верификацию почты, rate limiting, иногда ручное одобрение.

### 3. Нет ограничения частоты запросов к входу

Подбор паролей к форме входа **не ограничен** на уровне приложения. В продакшене — `django-axes`, fail2ban, WAF или rate limit на обратном прокси.

### 4. Режим DEBUG по умолчанию

Если в окружении не задан `DEBUG`, подставляется **`True`**. В продакшене обязательно `DEBUG=False` и надёжный `SECRET_KEY` только из переменных окружения.

### 5. Настройки HTTPS и cookies для продакшена не заданы

В `settings` нет (и для локальной разработки это нормально):

- `SECURE_SSL_REDIRECT = True`  
- `SESSION_COOKIE_SECURE = True`  
- `CSRF_COOKIE_SECURE = True`  
- `SECURE_HSTS_SECONDS` и связанные флаги  

Без них при работе по HTTPS сессия и CSRF-cookie могут передаваться небезопасно, если не настроен прокси.

### 6. Заголовки безопасности

Нет явной настройки CSP (Content-Security-Policy), `Permissions-Policy` и т.п. Для жёсткой политики часто используют `django-csp` или заголовки на nginx/Cloudflare.

### 7. SMTP и письма

Пароль почты в `.env`. Файл не должен попадать в git. При компрометации сервера секреты в окружении тоже утекут — ограничьте права на хосте и ротируйте пароли.

### 8. Логи каталога

В лог пишутся имена товаров и связанные поля — не персональные данные пользователей, но при расширении логирования не следует писать пароли, токены и полные данные форм контактов в открытый текст без политики хранения.

### 9. SQLite в файле

При использовании SQLite файл БД на диске должен быть недоступен для скачивания через веб-сервер и иметь права только у пользователя процесса приложения.

## Чеклист перед выкладкой в интернет

- [ ] `DEBUG=False`, `ALLOWED_HOSTS` — только ваши домены  
- [ ] Уникальный длинный `SECRET_KEY` в секретах окружения  
- [ ] PostgreSQL (или иная серверная БД), бэкапы  
- [ ] HTTPS за reverse-proxy; включить `SECURE_*` и secure cookies  
- [ ] Раздача `media/` и `static/` без листинга каталогов; медиа не в корне сайта как исполняемые файлы  
- [ ] Ограничить кто может менять товары и посты (роли / авторство)  
- [ ] Rate limiting на `/accounts/login/` и при необходимости на регистрацию  
- [ ] Актуальные зависимости (`poetry update`, проверка уязвимостей)  
- [ ] Отключить или защитить админку (сильные пароли, IP allowlist, 2FA на уровне провайдера при возможности)

## Итог

Для **локальной учёбы** текущий уровень приемлем: CSRF, пароли, ORM, валидация загрузок, защита `.env` от коммита. Для **реального хостинга** критично закрыть пункты из раздела «Риски» и пройти чеклист выше.
